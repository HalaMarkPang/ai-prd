# 成稿审查与事件通知规则

本文适用于已有 PRD 的审查、修订，以及通知、任务、申请等异步事件需求。它补充主技能的范围、接口和异常规则，不替代具体业务确认；不涉及的检查项应跳过。

## 1. 先确定读什么、改哪里

1. 区分参考材料、待审查文档和写入目标。收到新链接，只表示获得了新材料，不代表原修改目标已被替换。
2. “看看现在的”“检查遗漏”“只在对话中告诉我”按只读审查处理，不修改在线正文，不发布替代稿。用户要求“按A修改B”时，A只读，B是唯一写入目标；后续明确授权修改A时，才重新确定权限。
3. 每轮审查重新读取当前版本，包含与问题有关的表格、批注和图片。不能用上一轮快照代替当前稿，也不能把用户已经补充的内容再次列为遗漏。
4. 写入前核对目标地址、文档标识、标题及已有正文，并用一句话说明本次修改对象与范围。链接疑似拼写错误、打不开或与已确认目标不一致时，先核实；仍不能确定则询问，不自行改写文档标识并写入其他页面。
5. 在线更新保留修改前快照，提交前检查期间是否有他人编辑。发现变化后先合并，不覆盖新内容。更新后重新读取，核对只发生计划内修改；完成写入不等于已验证保存。
6. 误改恢复只撤销自己的改动。恢复前同样检查后续编辑；存在冲突时保留对方内容，并就无法判断的部分征求用户确认。操作日志或版本历史中的客观记录不得宣称已被恢复删除。

## 2. 审查只报告尚未解决的问题

先按“用户当前说明 → 最新成稿 → 已确认版本 → BRD → 历史材料”的顺序核对。意见分为三类：

| 类型 | 判断依据 | 输出方式 |
|---|---|---|
| 已覆盖 | 当前稿明确写出规则及必要边界 | 不再列为缺失；最多一句确认 |
| 仍有歧义或冲突 | 相同文字可导致两种行为，或与已确认规则不一致 | 指出冲突位置、具体情形及建议口径 |
| 实质缺口 | 某个实际可发生的输入或状态没有处理结果 | 写清该情形、后果和最小补充建议 |

- 用户排除的章节、本期不做或明确后续补充的内容，不纳入本轮遗漏清单。
- 做反向检查时，从具体失败情形出发，不为了凑条数否决方案。没有新增问题可以直接说明。
- 方案建议不等于已确认规则。用户说“可以”“ok”，不自动确认前文仍标为待确认的每个业务选项。
- 用户已确认的阈值、次数、触发渠道和流程顺序应保留。若存在冲突，说明影响并提出调整选项，不静默改动。

## 3. 把频控写成可执行的业务句子

不能仅写“按有效对象＋场景去重”。先区分三个概念：

| 概念 | 回答的问题 | 应写清的内容 |
|---|---|---|
| 发送资格 | 当前能不能执行？ | 业务状态、归属、权限及其他必要条件 |
| 去重身份 | 哪些请求属于同一件事？ | 业务实体的稳定身份、动作或卡片类型 |
| 次数约束 | 在什么范围内允许执行几次？ | 各动作的上限、时间窗口、计次结果及重置条件 |

1. 使用业务方认可的实体身份。顾客、订单、申请、会话、消息不等价；不能把“同一笔申请”自行改成“同一顾客＋订单”。确认订单与申请是否一对多、修改或重新提交是否仍属原申请，再选择口径。
2. “有效”“未完成”等状态是资格，不是稳定的去重身份。资格变化不能默认清除已有成功记录；是否形成新对象由业务来源系统确认。
3. 直接写“对象A的通知甲最多几条，通知乙最多几条”，明确是各自上限还是合计上限。明确限制覆盖对象生命周期、单日还是其他时间窗口，不能把“最多一次”理解成“每天一次”。
4. 对修改、撤销后重提、重开、跨组织及手动与自动操作，分别确认是否重置、共用额度或独立计次；仅检查本期可能出现的情形。BRD未明确时列为待确认，不自行禁止或放开。
5. 补发及不同终端展示是否新增计次必须明确。同一消息的展示副本不等于多条业务通知。

**写法示例，仅用于说明表达方式，不是默认业务规则：**

> 同一笔申请，申请通知、到期提醒各最多一条；重复通知不新增消息。部分投递失败只补失败部分，已成功的部分不重复。修改或重提是否视为新申请，由申请系统确认。

## 4. 去重、重试和状态校验必须兼容

资格决定能否继续，执行结果决定恢复范围。两者分别检查，不能用其中一个替代另一个。

### 4.1 资格校验与查询时机

- 明确谁触发事件、谁判断资格、谁执行动作，以及采用哪个系统的状态。发送方不能仅凭“收到成功通知”推断执行时仍满足条件。
- 事件排队、延迟或重试可能导致状态过期。此时须定义首次执行、延迟执行及再次尝试前的校验方式；若确认以主动查询保证新鲜度，正文应写明查询责任和时机，不能只写在依赖列表中。
- 查询结果至少区分允许、不允许、未知。未知包括失败、超时、空结果及无法解释的状态；资格未确认前不得按允许继续，后续是重查、结束还是转处理，应有明确口径。
- 不机械增加重复查询或持续轮询。已有可信校验可复用时说明依据；查询之后、执行之前状态仍可能变化，不能把“已查询”写成消除所有竞争的保证，关键边界由相关系统共同确认。

### 4.2 成功、失败和未知结果

| 情形 | 必须明确的处理 |
|---|---|
| 已成功 | 不重复执行；同一请求再次到达复用已有结果 |
| 明确失败 | 按确认的次数、范围和条件恢复；次数耗尽后的记录、反馈与处理责任清楚 |
| 结果未知 | 先核实原结果，不能因超时就认定失败并另起一次动作 |
| 部分成功 | 按实际投递目标区分，只恢复失败部分；不因“存在成功消息”把失败部分也判为完成 |
| 多端展示或离线 | 按实际承接判断投递结果；离线、未读、渲染失败不能直接等同发送失败 |

- 并发请求可能同时查到“未发送”。PRD约束最终只能产生规定数量的业务动作，不指定锁、存储、事务等实现方案。
- 重复通知、并发调用、创建后重试都需复用已创建的业务资源；不能仅避免重复消息，却创建出多个会话或任务。资源匹配同时校验用户、业务单据与所属组织等归属，不能仅按用户身份跨业务选择。
- 上限必须覆盖同一次动作的所有入口，不能让事件重投或再次回调反复重置重试预算。若业务允许另起人工恢复流程，单独说明其权限与边界。
- 恢复前再次判断当前资格。状态已失效就停止尚未成功部分；已完成部分及历史记录如何保留单独说明。
- 跨端部分成功时，明确用户能看到什么。未确认送达不能显示“对方已收到”；后台失败不能回滚无关的已成功业务。
- 查询重试、会话恢复、消息投递重试是不同操作，不混用次数。用户已确定某一步的次数则保留；未给出的其他次数、时限和技术参数仍待确认。

## 5. 检查自动操作对既有链路的影响

1. 系统代用户发送时，分别确认展示身份和自动化来源。按用户消息展示，不代表所有下游都应按真实用户主动输入处理。
2. 检查下游环节，例如会话或工单创建、分配、机器人或 Agent 自动应答、未读与提醒、时效统计。只列本场景实际经过的环节，不默认全部豁免或全部沿用。
3. 用户已确认“不触发Agent应答”等规则时，保留该结论并明确如何验收；没有确认时提出建议，不把它迁移为所有通知场景的默认值。
4. 历史展示与当前可操作状态分开。若保留历史快照，点击入口仍需按目的系统规则查询状态及鉴权；不能让旧卡绕过权限、重复办理或创建新业务。

## 6. 简化表达，不删除关键条件

- 每条规则尽量写成“具体对象／触发条件 → 处理动作 → 结果或终止条件”。用业务名称替代未定义的“场景”“对象”“有效”等词，不用“做好兜底”“保证一致”等空泛要求代替行为。
- 对话审查先给结论，再列最重要的未解决项。用户要求简短时优先控制在3—5条；每条包含问题和处理建议，不展开通用方法论。不要把“是否应该执行”的答案重新写成一个问句。
- 正文只保留一处完整规则，其余章节简要引用。已解决的评审问句应在获准修改后删除或改为结论；尚未确认的事项仍保留待确认状态。
- 时序图保留角色、触发差异、必要状态查询、执行前提和主要输出。同一后续链路合并绘制；只有控制不同结果的关键分支才保留。
- 异常、重试、计次和字段细节放正文。图中校验失败的路径不能继续执行；合并分支不等于删除条件。渲染后检查实际文档宽度下是否清晰，不能只检查语法通过。
- 技能沉淀采用通用判断规则与检查样例。具体时限、次数、固定文案、接口渠道及策略豁免仅属于原项目；不写入其他项目默认值，不携带原稿人员、业务指标或在线文档标识。

## 7. 使用前后检查

- [ ] 参考材料、审查对象、写入目标及本轮授权已区分；目标不能确定时未写入。
- [ ] 意见来自最新版本，未重复已解决内容，也未扩展用户排除的范围。
- [ ] 频控明确业务实体、动作、各自或合计上限、时间窗口及重置边界。
- [ ] 去重不会吞掉失败部分；超时、并发、事件重投和离线没有触发重复业务。
- [ ] 资格未知不继续；状态校验责任、时机及重试结束条件明确。
- [ ] 自动操作的下游影响及历史点击后的权限、状态校验按本项目确认。
- [ ] 流程图只有必要主干且关键前提未丢失，正文没有重复堆叠。
- [ ] 未将方案建议或某一项目的参数写成通用已确认规则。
