# 就绪度问诊

本文件定义任务开始时如何盘点材料、判断缺什么，以及怎样集中向用户提问。目的是让陌生用户拿到技能后，模型先说清“现在能做什么、还缺什么、缺了会怎样”，而不是直接生成一份看似完整却建立在猜测上的 PRD，也不是没完没了地追问。

## 1. 适用时机

| 任务模式 | 问诊范围 |
|---|---|
| 完整生成 | 全部八项检查，集中一轮提问 |
| 评审精简稿 | 重点检查格式样稿、范围和读写目标 |
| 局部修订 | 只确认修改目标、修改范围和必须保持不变的内容 |
| 只读审查 / 样本学习 | 不做完整问诊；仅当审查对象或范围不清时确认一次 |

问诊发生在确定任务模式之后、需求评估之前。用户在首条消息里已经说明“不用问，直接写”时，跳过提问，但仍要在开头列出采用的默认假设。

## 2. 先自己查，再问用户

提问前先完成以下动作，能自己拿到的信息不问：

1. 读完用户提供的全部材料，包括附件、链接（能访问时）、截图、表格和已有 PRD。读取方法见 [材料来源](doc-sources.md)。
2. 用户给了代码路径或仓库时，先做一次定向检索，判断现状线索是否充足。方法见 [代码证据](code-evidence.md)。
3. 从材料中提取已有答案。材料里已经写明的内容不再提问，只在冲突时请用户裁定。

## 3. 八项就绪度检查

| 编号 | 检查项 | 要回答的问题 | 典型阻塞情形 |
|---|---|---|---|
| A | 任务与交付 | 这次是新写、精简、局部修改还是只审查？交付成全文、片段还是对话反馈？写到哪里、是否允许写入？ | 不知道写入目标；要修改在线文档但未授权 |
| B | 需求材料 | 有哪些材料，能否完整读取？ | 只有链接但无法访问，且无其他材料 |
| C | 问题与目标 | 要解决什么问题？有什么证据（数据、反馈、事故）？怎样算成功？ | 只有方案没有问题，无法判断是否值得做 |
| D | 用户与场景 | 谁在什么场景下使用？涉及哪些终端？不同角色的数据范围是否不同？ | 角色和权限不清，影响功能规则 |
| E | 范围 | 本期做什么、明确不做什么？哪些方案已经确认、不许改？ | 范围无法判断，可能写多或写少 |
| F | 现状与代码 | 是否在已有系统上改？代码或接口文档在哪里，能否访问？ | 改造型需求但现状完全未知 |
| G | 格式 | 有没有自己的模板、样稿或指定语言风格？ | 一般不阻塞，可用本技能的 PRD 模板 |
| H | 约束与依赖 | 上线时间、外部团队、合规要求、已确认的阈值或文案？ | 涉及不可逆或高影响动作，但规则未定 |

每项归为三类：

- **已具备**：材料中有明确答案。
- **可假设**：缺失但影响低，或有合理默认值。写明默认值，后续进入“待确认”。
- **阻塞**：缺失会导致范围错误、权限错误、不可逆操作或结论不可信。只有这一类和高影响的“可假设”项才进入提问。

## 4. 提问规则

1. **一轮集中问完。** 把所有需要用户回答的问题放在同一条消息里，不连续多轮追问。
2. **最多 5 个问题**，按影响从高到低排列。超过 5 个时，低影响项改为默认假设。
3. **每个问题写清三件事**：问什么、为什么影响结果、用户不回答时按什么默认处理。
4. **优先给选项。** 客户端提供结构化提问或选择题工具时优先使用；没有时用编号选项，并保留“其他”。
5. **允许跳过。** 明确告诉用户可以回答“按默认”或“直接写”，此时带着假设继续。
6. **不问能自己查到的事**，不问与本期决策无关的事，不把方法论问题抛给用户。
7. **不索要敏感凭证。** 需要代码或文档访问权限时，指导用户在本机配置环境变量或本地导出，不要求把 token、密码、cookie 贴进对话。

## 5. 输出格式

首次响应使用以下结构，整体保持简短：

```markdown
**我对这个需求的理解**：<一到两句话复述需求和本次任务模式>

**就绪度**

| 项 | 状态 | 说明 |
|---|---|---|
| 需求材料 | 已具备 | 已读取 BRD 全文及 3 张原型图 |
| 问题与目标 | 阻塞 | 只有方案，缺少问题证据和成功判据 |
| 现状与代码 | 可假设 | 未提供代码；现状结论将全部标为待确认 |
| … | … | … |

**需要你确认的问题**（不回答的按默认处理）

1. <问题>
   - 为什么问：<影响>
   - 选项：A / B / C
   - 默认：<不回答时的处理>

你也可以直接回复“按默认继续”。
```

材料已经齐全时，只输出理解和就绪度结论，然后说明将直接进入需求评估，不为走流程而提问。

## 6. 代码现状的问法

改造型需求必须问清代码访问情况。推荐问法：

> 这个需求要在已有系统上改。为了让 PRD 里的现状描述有依据，我需要看代码。你的代码在哪里？
>
> - A. 不提供代码：涉及现状的结论我会全部标为“待确认”。
> - B. 我贴关键代码片段或接口文档：只基于你贴出的内容下结论。
> - C. 仓库已在本机：告诉我路径，我只读检索。
> - D. 仓库在 GitHub / GitLab 等远端：我用只读方式查询，需要你在本机配置只读 token。
> - E. 跨多个仓库、调用链复杂：建议先建代码图谱再检索。
>
> 默认：A。

各选项对应的证据级别、接入步骤和召回边界见 [代码证据](code-evidence.md#1-代码访问分级)。用户选择后，在后续产物中注明实际采用的级别。

## 7. 回答之后

1. 用户的回答作为“用户明确说明”记入事实来源，优先级高于原始材料。
2. 回答引出新的阻塞项时，可以再问一次，但只问新问题，且最多追加一轮。
3. 进入需求评估后，过程中再遇到缺口，按低风险假设推进，并列入“待确认”；只有涉及权限、不可逆动作或高影响结果时才中断确认。
4. 用户选择跳过的项，在 PRD 开头或待确认章节写明采用的默认假设。

## 8. 非交互运行

通过脚本、CI 或其他无人值守方式调用时无法提问：

1. 照常完成八项检查。
2. 不等待输入，把就绪度结论写入工作目录或 PRD 开头的“生成说明”。
3. 阻塞项全部进入“待确认问题”，并注明“非交互生成，未经用户确认”。
4. 不能因为无法提问就把假设写成既定事实。
