# PRD 生成规则

本文件定义把需求材料转化为研发可评审 PRD 的执行模式、前置约束、执行步骤与验证要求。入口与问诊见 [SKILL.md](../SKILL.md) 和 [就绪度问诊](intake.md)。

## 输入与输出

输入：以下一种或多种材料。

1. BRD、业务背景、会议纪要、需求邮件、一句话需求。
2. 在线文档链接，本地 Markdown、Word、PDF、Excel、HTML、TXT。读取方法见 [材料来源](doc-sources.md)。
3. 截图、原型图、流程图、线上页面截图。
4. 已有 PRD、历史评审意见、用户补充说明。
5. 代码库路径、仓库地址或业务系统名称，用于按需检索已有能力、接口边界和技术约束。

输出：按任务模式交付 PRD、修订片段或审查结论。生成和修订内容按适用范围满足以下条件。这些是信息检查项，不是每份正文都必须设置的章节：

1. 问题证据、目标、现有能力、本期变更、保持不变与非目标清楚。
2. 角色、业务对象、工作上下文、数据范围及操作权限清楚；只展开影响结果的差异。
3. 适用条件、触发、处理、可观察结果和后续状态清楚；涉及时间、异常与恢复时说明相应边界。
4. 有界面的需求写清入口、操作与相关状态；无界面需求不强制补页面和弹窗。
5. 数据语义、来源及验收清楚；功能正确性、运行质量与业务效果分开验证。埋点默认不进入链路和功能需求，只有用户明确要求时才单独输出。
6. 已有能力、本期变更、建议和待确认不混用，不擅自修改已确认的业务规则。
7. 研发能据此确定实现边界，测试能据此写出用例；只读任务到反馈结束，不生成额外正文。

## 按任务读取补充规则

先读取 [通用需求分析与表达方法](requirement-method.md)，按当前任务选择适用检查。其六个分析阶段嵌入下文步骤，不增加第二套流程或额外产物：问题与目标（步骤 2—3）→ 变更基线（步骤 4—5）→ 业务模型（步骤 6）→ 规则定义及数据、交互与依赖（步骤 5—7）→ 验证与交付（步骤 8—9 及验证步骤）。

审查或修订已有成稿，以及处理通知、任务等异步事件需求时，还必须读取 [成稿审查与事件通知规则](review-and-notification-rules.md)。对照 [检查样例](review-regression-cases.md) 做必要验证；不适用的业务项不强制添加。

纯审查或“只在对话中告诉我”到意见反馈结束，不进入正文生成或在线写入。用户当前说明和已确认业务规则优先，补充规则中的示例不能替代本项目决策。

## 前置约束（执行前必须理解）

下列约束优先于模板形式。未满足这些约束时，不得声称 PRD 已完成。

1. **BRD 到 PRD 不是扩写。**
   BRD 通常说明业务目标和方向，PRD 必须把目标转为明确的业务行为与可验证结果。涉及角色权限或数据范围差异时，给出功能、角色、数据范围与无权限表现；单角色也要检查是否存在范围限制。只在组合关系需要比较时使用矩阵，不添加没有实际差异的权限章节。

2. **先评估需求是否成立，再建需求模型。**
   新建需求在材料解析后、建模前，从产品经理视角评估真实性、必要性、替代方案与范围边界，区分问题证据和原因假设。结论为“建议做 / 不做 / 调整范围 / 替代方案”并附依据；需要查证才能判断时，先定向核对再收敛。结论不成立时先与用户对齐，不强行生成。局部修订只检查变更影响；只读审查、样本学习不重新评估全部既定方案。

3. **先建需求模型，再写正文。**
   标准顺序：就绪度问诊 → 材料解析 → 需求评估 → 约束提取 → 需求模型 → 缺口识别 → PRD 初稿 → 质量审查 → 修订输出。未确认用户、场景、范围、已有能力和禁止修改项之前，不直接写全文。

4. **不把已有能力、本期新增和推断混在一起。**
   关键结论标注来源类型：`用户明确说明`、`原始材料`、`已有 PRD`、`代码/系统现状`、`合理推断`、`待确认`。涉及研发实现或业务规则时，禁止把推断写成事实。

5. **不擅自优化用户已确认的业务逻辑。**
   用户要求“其他不要改”“只补这一段”“保持原逻辑”时，锁定修改范围。确需联动修改时，先说明冲突点、影响范围和修改原因。

6. **代码库只做按需检索，不做全量蒸馏。**
   对大型代码库，只围绕当前需求的模块、关键词、接口名、页面名、业务系统名做定向检索，提取已有能力、技术边界、复用可能和依赖风险。不先生成全仓摘要。访问级别与方法见 [代码证据](code-evidence.md)。

7. **缺信息时：开场集中问，过程中按低风险假设推进。**
   任务开始时按 [就绪度问诊](intake.md) 集中提一轮问题。之后再发现缺口，先写“暂按以下假设处理”，并列入“待确认问题”；只有缺失信息会导致严重误判、错误实施或高风险后果时才中断确认。

8. **PRD 面向研发评审，不写咨询报告腔。**
   用产品经理视角，表达严谨、直接、可执行。避免空洞价值表述、宣传式表述和无法验收的收益描述。

9. **先压力测试范围，再生成 PRD。**
   BRD 常混有业务期望、竞品参考、二期想法、指标假设和多个系统的范围。生成前先判断哪些属于本期研发交付，哪些只是背景、观察指标或后续评估。不要把 BRD 中出现的其他页面、AB 实验、运营动作、自动化营销等内容直接写进本期范围，除非用户明确要求且材料中有研发承接依据。

10. **优先贴合用户的 PRD 格式。**
    用户提供了自己的模板或样稿时，正文结构优先采用它。不套用通用框架；不新增模板中没有、且本需求不需要的评分模型、复杂权限章节或风险章节。用户模板的一级结构与本技能的 PRD 模板不同时，把范围、现有链路、外部依赖、验收、跨团队依赖、待确认问题和代码线索归入用户模板的对应章节，不额外拆成独立的一级章节。

11. **指标口径不清时只写观察指标，不写目标承诺。**
    BRD 中的转化率、收入、点击率、提升幅度等数字，只有口径、数据源、时间窗、分子分母和归因方式都明确时才能写为目标；否则写为“上线后观察指标”或“待数据侧确认”，不写“目标提升至 XX”“正向提升”等未确认承诺。同一指标全文只定义一处口径，其余引用。

12. **PRD 不替研发定义接口协议。**
    涉及外部接口、跨系统接口、RPC、HTTP API、消息队列或后端聚合接口时，PRD 只写产品侧的“数据需求、业务含义、用途、异常处理要求”。字段英文名、字段类型、错误码、超时阈值、缓存策略、重试策略、接口路径和协议结构由研发在技术方案中定义，除非来自已确认的接口文档。
    用户或已确认材料规定的业务重试次数、作用对象和终止结果应保留，不作为“擅自定义协议”删除；但不能据此补造未给出的退避、超时或其他环节的重试参数。

13. **链路说明保持简洁。**
    只说明触发、必要信息、处理责任、关键校验和输出。不预设“前端取参、后端聚合”等固定架构；有已确认的现有链路时据实说明本期变化。链路与功能需求不写埋点；同一内容不用段落、表格和图重复表达；只有参与方规则确实不同时才分别说明。

14. **可变信息定义时效和更新规则。**
    区分展示信息、执行资格与历史记录，说明信息来源、允许的时效、查询与更新时机，以及失败时的结果。纯展示可以采用“查询时快照 + 关键入口重新查询”，但要有本项目依据；影响交易资格、权限或其他高影响操作时，明确执行时的有效性要求。历史记录与当前可操作性分别定义。不由“强一致”直接推出订阅、轮询或某种缓存方案，技术实现由研发确认。

15. **Mermaid 图可读、少线、无交叉。**
    优先单向链路（TB 或 LR），避免多分支回流造成交叉。不同系统用 subgraph 或 classDef 区分；使用颜色时至少区分前端、后端、外部依赖和数据来源。流程图只表达业务与系统链路，不画埋点节点。节点文字换行用 `<br/>`。生成后用 Mermaid 渲染工具验证；线条交叉或系统边界不清时重画。
    图形选型：单业务流程用流程图；跨系统职责划分用泳道图；强调时序与消息往返用时序图；页面跳转用跳转图；端到端体验用旅程图。简单链路只用步骤列表，不强行画图。
    多入口共用后续逻辑时合并绘制，保留关键校验前提及结果；异常、补发、计次和字段细节放正文。不为简化图删除“校验通过才执行”等控制条件。语法渲染通过不等于可读，按实际文档宽度检查。

16. **先识别输出模式，再决定文档形态。**
    用户让“生成完整 PRD”时走完整生成；用户给了已有 PRD、自己的模板或说“给研发评审看”时走评审精简稿；用户只要求补 AB、补规则、补某个章节时只输出可插入的章节；用户明确要求补埋点时才单独输出埋点章节；用户让“看看我的 PRD / 学语言和布局”时先分析风格，不急着补全文。

17. **用户已有 PRD 的语言和布局优先于通用模板。**
    用户提供已有 PRD、在线成稿、样稿或模板时，先学习标题写法、章节层级、表格字段、链路描述、功能颗粒度、待确认问题写法和代码线索保留程度，不用通用框架覆盖用户风格。

18. **评审稿要精简，内部推理不进最终正文。**
    给研发评审的 PRD 只保留背景与目标、范围、现有链路、本期变更、功能规则、数据与接口需求、非功能、验收、跨团队依赖、待确认问题。需求评估、事实抽取、需求模型、审查报告和评分是内部质量控制产物，除非用户明确要求，不写进最终 PRD。

19. **链路说明优先写“现有链路 / 本期变更”。**
    在已有系统上补能力时，说明现有路径、本期在哪个节点变更、哪些行为保持不变。只有已确认采用某种前后端分工时才按该架构描述，不把一种实现设为默认。

20. **展示类需求按页面或位置组织，规则集中。**
    展示、标签、字段、入口类需求按“端 → 页面/位置 → 需求详情”组织；页面章节只回答在哪里展示、展示什么、是否影响现有内容、异常时页面怎么处理。字段口径、展示文案、刷新规则、异常规则集中在“规则说明”，不在每个页面重复。

21. **接口章节不擅自写技术协议。**
    除非用户提供已确认的接口文档，接口章节不写字段英文名、字段类型、接口路径、扩展方案、错误码、超时阈值、缓存策略和重试策略，只写“数据需求、业务含义、用途、异常处理要求”。

22. **AB 实验按用户意图处理，不机械补全。**
    完整生成模式且材料包含 AB 时补 AB 方案；用户说 AB 还没写时，不当作漏项，只说明后续可补的位置；用户成稿已把 AB 移出本期时，不从 BRD 硬拉回功能需求，只放后续事项或待确认。

23. **指标写法优先用“当前口径 / 本期处理”。**
    口径或归因不完整时，用“指标 | 当前口径 | 本期处理”表，写明“作为上线后观察指标，不作为本期研发验收指标”。同一指标只在一处定义口径（以指标名为去重键），其他章节引用。

24. **代码检索结论默认放末章。**
    正文只保留与产品边界相关的结论；详细路径放“代码线索”表，默认字段为“线索 | 文件”。不把代码分析写成技术方案。

25. **待确认问题只列影响落地的问题。**
    待确认问题必须影响研发设计、排期、验收、上线风险或跨团队协作。不堆砌业务愿景、方法论问题或低风险的文案细节。

26. **“外部依赖”只写外部产品和系统。**
    只列当前产品落地需要依赖、对接或确认的外部产品和外部系统。本端前端、承接后端、内部配置服务、策略服务、代码模块、数据侧指标确认等，放在链路说明、数据与接口需求、跨团队依赖、待确认问题或代码线索中。

27. **链路和功能需求默认不写埋点。**
    现有链路、本期变更、流程图、功能需求、数据与接口需求、验收标准、跨团队依赖中都不夹带埋点。只有用户明确要求“补埋点”“写埋点方案”时才单独输出埋点章节。

28. **基于用户成稿修订时，先尊重既定方案，再补缺口。**
    用户已提供成稿、原型或已写好的交互逻辑时，保留其入口命名、操作方式、页面结构、提示口径、流程顺序和对接人信息；只修正明显错字、表达不严谨、链路不闭合、异常缺失、评审痕迹、口径冲突和风险文案。确需调整既定逻辑时，说明冲突点和影响范围。

29. **交互型需求按状态变化定义行为。**
    涉及连续操作、异步处理或跨端分发时，检查“适用对象与条件 → 触发 → 校验与处理 → 结果与反馈 → 后续状态”。按实际功能核对默认态、操作中、完成、失败、取消、恢复及跨端影响；加载、空值、错误、无权限与弱网不能混为一种结果，但只说明本需求存在的状态，不凭检查表新增控件或功能。

30. **失败处理集中收口。**
    同一链路的前置校验失败、文件或数据获取失败、第三方处理失败、空结果、策略拦截、消息或任务提交失败、展示失败等，优先用“失败情况 | 处理逻辑”表。处理逻辑说明：是否继续主流程、是否进入下游系统、是否生成业务记录、是否支持重试/重发/撤销、用户提示口径和恢复方式。

31. **策略拦截文案不暴露判断细节。**
    风控、审核、合规、权限、资质等策略类拦截，不直接写“包含违规信息”“命中风控”“审核拒绝原因”等可能暴露策略判断的提示，除非已有确认文案。默认写“按现有策略失败口径提示，具体文案以策略方确认为准”。策略拦截与普通系统失败区分：普通失败通常引导重试；策略拦截通常阻断下游动作。

32. **外部依赖写到可验收。**
    写清提供方、消费方、输入与输出的业务含义、结果用途、失败处理和确认状态。复用现有能力时注明依据；涉及展示、历史查询、多端或版本差异时补充对应边界。不能只写系统名和对接人，或用“兼容”“支持”等泛词代替可验证的责任。

33. **AI / Agent 类需求写清模型输入、输出与工具调用规则。**
    需求属于 AI 或 Agent 能力（智能回复、内容润色、意图识别、推荐、自动处理、工具自动调用等）时，功能需求补“AI/Agent 能力要求”一节：能力类型与边界、模型可见输入清单、输出结构与语气、是否可调用工具、是否需要人工确认、逐工具调用规则、置信度分层与拒答、上线后的 Badcase 与迭代。产品侧只定义“什么条件下调用什么工具、需要哪些信息、缺失/超时/失败怎么处理、结果怎么用”，不定义模型结构、Prompt 全文和接口协议。红线：不得编造业务数据（如订单、账户、工单状态）或工具执行结果；工具调用前置条件不满足时不得伪造调用；没有新信息、新方案、新工具时不重复应答；对外身份与必要披露按项目确认，不伪造服务主体。

## 执行模式

执行前先判定模式。模式决定最终输出形态，不降低内部严谨性。

| 模式 | 触发条件 | 最终输出 |
|---|---|---|
| 完整生成 | 用户要求从零生成完整 PRD；提供模板时仍按此模式，并沿用模板格式 | 完整 PRD，同时产出 requirement-assessment、source-facts、requirement-model、review-report 作为内部留痕，默认不进正文 |
| 评审精简稿 | 用户提供已有 PRD、自己的模板或样稿；或明确“给研发评审看” | 研发评审稿；不输出内部评分和长篇推理 |
| 局部修订 | 用户只要求补 AB、接口、规则或某个章节；或明确要求单独补埋点 | 可直接插入的章节或改写片段；不重写全文 |
| 只读审查 | 用户让“看看我的 PRD”“学语言和布局”“这个技能有没有要改的” | 风格、结构、规则分析；必要时给出修改建议；不急着补正文 |

模式判断规则：

0. 明确的任务要求优先于材料形式：只读审查和局部修订先分流；明确要求从零完整生成时，即使有模板也按完整生成，模板只决定格式。
1. 用户已有成稿时，先以成稿范围和风格为准，再回看 BRD 是否有未处理的材料。
2. BRD 是输入，不等于本期 PRD 的全部范围。用户成稿、修订记录、当前说明已经收敛范围时，不把 BRD 中被剔除的内容重新塞回功能需求。
3. 只读审查模式重点看语言、布局、范围取舍、规则表达和技能是否需要改，不把“漏项”作为默认主结论。
4. 用户要求“再看现在的”时重新读取最新版本，只反馈本轮范围内尚未解决的歧义、冲突或缺口；已补充的内容不重复列为遗漏。
5. 参考材料和写入目标分别确定。用户要求“按 A 修改 B”，只读 A、修改 B；链接无法核实，或仅授权审查时不写入。

## 执行步骤

### 步骤 1：建立工作目录

完整生成模式建议建立独立工作目录，保存原始材料、中间模型和输出文档。其他模式可不强制建目录，但必须保留关键输入来源。

```bash
workdir="<目标目录>/<需求名>-prd-work"
mkdir -p "$workdir"/inputs "$workdir"/outputs "$workdir"/reviews "$workdir"/research
```

建议的文件命名：

```text
inputs/BRD.md
inputs/source-notes.md
inputs/screenshots/
research/code-context.md
research/code-evidence.md
outputs/intake.md
outputs/requirement-assessment.md
outputs/source-facts.md
outputs/requirement-model.md
outputs/PRD.md
reviews/review-report.md
```
### 步骤 2：获取与整理输入材料

按 [材料来源](doc-sources.md) 读取全部材料，完成完整性和版本核对，然后完成 [就绪度问诊](intake.md)。完整生成模式把就绪度结论和用户回答保存为 `outputs/intake.md`。

有参考 PRD 时，在建模和写作前提取结构、术语、规则颗粒度和确认状态。按 [材料与样本使用](requirement-method.md#2-材料与样本使用) 区分当前有效规则、历史删改、候选方案和模板残留。只读审查输出可迁移的方法及证据边界，不重新生成原稿。

### 步骤 3：需求评估（生成前置闸）

材料读取后、抽取约束与建模前，先从产品经理视角评估需求本身。收到需求的第一动作是判断它是否成立，而不是直接产出 PRD。评估至少覆盖四项：

- 需求真伪：是否真实问题，是否把技术障碍误当需求。
- 必要性：是否值得做、本期是否该做。
- 替代方案：是否存在更低成本或更优的方案。
- 范围边界：如果做，做到什么程度。

结论采用“建议做 / 不做 / 调整范围 / 替代方案”，附依据和未决限制。“建议做”或“调整范围”进入后续分析；“不做”或“替代方案”先与用户对齐，不强行生成。

两条红线：不得收到需求即产出 PRD；评估须给出有依据的结论，不把可以自行判断的事项变成连续追问。问题证据与原因假设分开；需要代码或外部能力查证才能判断时，先执行步骤 5 的必要只读核对。后续查证推翻前提时，返回修订评估结论。

完整生成模式输出 `outputs/requirement-assessment.md`；其他模式可在内部完成评估，但必须先有结论再继续。

```markdown
# 需求评估结论

## 结论
建议做 / 不做 / 调整范围 / 替代方案（四选一）

## 依据
- 真伪：...
- 必要性：...
- 替代方案：...
- 范围边界：...

## 需用户对齐项（若有）
- ...
```

完整生成模式输出 `outputs/source-facts.md`；其他模式可在内部完成。

```markdown
- 功能颗粒度：...
- 待确认问题写法：...

- ...

## 5. 非本期范围
- ...

- ...

## 7. 本期新增能力
- ...

- ...

| 编号 | 类型 | 描述 | 涉及材料 | 处理建议 |

| 编号 | 问题 | 不确认的风险 | 默认假设 |

```

事实处理要求：

1. 优先级：用户当前说明（含问诊回答）> 用户已有 PRD 成稿 > 最新确认版本 > 正式 BRD > 历史材料 > 推断。
2. 用户成稿与 BRD 范围不一致时，先判断是否为主动收敛；主动收敛时按成稿范围处理，不把 BRD 全量诉求回灌。
3. 修改记录中标明“本期不做”“后续再补”“暂不交付”的内容，不进入本期功能需求。
4. 问题证据与原因判断分开；删除线、待定问句和模板示例不视为已确认规则。版本或图文冲突没有确认依据时，列明影响，不自行选择。
5. 建立现有能力、本期新增/修改/取消、保持不变、非目标和实施前提的变更基线。涉及配置或默认行为时，再核对新增对象、存量对象、人工设置、继承及冲突，不另造固定的迁移策略。

### 步骤 5：按需查证研发现状

按问诊确定的代码访问级别执行定向检索，方法见 [代码证据](code-evidence.md)。目标是回答“能否复用现有能力、边界在哪里、PRD 需要写清哪些约束”。

```markdown

检索范围：<仓库、分支、路径>

## 1. 可复用能力
| 线索 | 文件 |
|---|---|

## 2. 技术边界
- ...

## 3. PRD 需要显式说明的依赖
- ...

## 4. 不确定项
- ...
```

检索结果只能作为现状线索。除非已读到明确的代码或接口定义，否则不写成确定事实。涉及改造范围或根因判断时，按 [证据档模板](../templates/evidence-template.md) 输出 `research/code-evidence.md`。

### 步骤 6：建立需求模型

完整生成模式输出 `outputs/requirement-model.md`；评审精简稿可在内部建模，最终正文不展示模型。

需求模型按 [业务模型与规则定义](requirement-method.md#4-业务模型与规则定义) 覆盖适用问题，不把每个问题变成必填章节。角色、工作上下文、可见数据与生效对象分别判断；纯规则调整可用决策表，无界面需求跳过页面问题：

1. 用户是谁？
2. 用户为什么要使用？
3. 在什么场景触发？
4. 入口在哪里？
5. 本期做什么？
6. 本期不做什么？
7. 系统先判断什么？
8. 用户可以做什么？
9. 操作后状态如何变化？
10. 失败时怎么办？
11. 权限不足怎么办？
12. 多端是否一致？
13. 如何记录数据？
14. 如何判断功能成功？
15. 测试如何验收？
16. 是否属于 AI / Agent 能力？如果是，模型能看到什么、输出什么、可调用哪些工具、什么条件下拒答或转人工？

推荐结构：

```markdown
# 需求模型

| 本期范围 |  |
| 非目标 |  |

## 4. 核心链路
```

### 步骤 7：生成 PRD 正文

正文结构先对齐用户提供的模板、成稿或样稿。没有模板时，以“问题目标、范围变更、方案规则、依赖约束、验证与待确认”为内容骨架，参考 [PRD 模板](../templates/prd-template.md) 按需求复杂度裁剪；内容骨架不等于固定的一级目录。简单变更可以只写现状、变更规则与验收条目，复杂关系再增加表格或图示。

结构硬门禁：

1. 用户提供了自己的模板或样稿时，一级结构必须与其对齐，不用本技能的 PRD 模板覆盖。
2. 出现以下情况判定不合格，必须重排：一级结构与用户模板不一致；写入本需求不需要的权限矩阵；新增模板没有的独立风险章节或评分章节。
3. PRD 模板是用户没有模板时的可裁剪参考。表格只保留适用内容，空表和逐项“不涉及”不进入正文；需要澄清的范围排除另行说明。
4. 共性规则在一处定义，差异分别说明；跨端完全一致时明确引用公共规则，不为形式完整重复正文。删除或改名用户原稿的章节，仍须符合本轮授权。

写作要求：

1. 语言严肃、明确，先结论后依据；使用可识别的主语、对象、动作和条件，不以评价词替代规则。
2. 已确定范围明确标为本期；假设、建议、待确认与已确认结论分开。
3. 规则按“适用对象与条件 → 触发 → 校验与处理 → 结果与反馈 → 后续状态”核对，正文不必机械套长句。
4. 按主要决策对象组织功能；有界面时说明页面与操作，无界面时说明业务规则及其结果。
5. 单一结论用条目，多条件映射用表格，复杂关系才用图。
6. 共性规则集中，差异明确引用；不用长段落、明细表和图重复表达同一链路。
7. 代码结论不替代产品规则；“沿用现有逻辑”要指出具体范围或可追溯的依据。
8. 对接人、接口、SLA 和指标目标未确认时，不编造。
9. 用户明确的标题、术语和结构优先；无指定样式的新稿使用中性标题，不为排版偏好改写已有成稿。
10. 历史数据注明来源、时间及适用范围；未核实或可能失效时标“待复核”。
11. 非交互生成或用户跳过了问诊问题时，在正文开头的“生成说明”中列出采用的默认假设。

### 步骤 8：内部审查

生成后必须执行审查，审查报告默认是内部产物，除非用户明确要求，不写入最终 PRD。

按需求涉及的方面执行 [验证与交付](requirement-method.md#7-验证与交付)：核对问题与变更的关系、边界、适用规则和验收的对应性，以及正文、图示和数据口径的一致性。无界面或无跨端需求跳过相应项；未执行的产品测试不标为通过。

```markdown
# PRD 审查报告

## 1. 范围审查
- 本期范围是否清楚：通过/不通过
- 存在容易误解的排除项时，非目标是否写清：通过/不通过/不适用
- 是否把 BRD 中的后续内容误写进本期：通过/不通过
- 问题与修订：...

## 2. 逻辑审查
- 主链路是否闭合：通过/不通过
- 新旧链路是否衔接：通过/不通过
- 条件的互斥、叠加及优先级是否与处理结果一致：通过/不通过/不适用
- 问题与修订：...

## 3. 页面与交互审查
- 页面/位置是否明确：通过/不通过
- 默认状态是否明确：通过/不通过
- 异常反馈是否明确：通过/不通过
- 多端差异是否拆分：通过/不通过
- 问题与修订：...

## 4. 研发边界审查
- 是否能转成接口、字段和状态：通过/不通过
- 是否只写产品侧数据需求，未替研发定义协议：通过/不通过
- 是否清理了无来源的协议与技术参数，同时保留有确认依据的既有接口和业务重试规则：通过/不通过/不适用
- 外部依赖是否明确：通过/不通过
- 代码线索是否只作为线索，且标明了访问级别：通过/不通过
- 问题与修订：...

## 5. 测试审查
- 每条适用规则是否可验收并能对应具体情形：通过/不通过/不适用
- 功能正确性、运行质量与业务效果是否分别核对：通过/不通过/不适用
- 边界值、数据语义、权限与异常是否有明确结果：通过/不通过/不适用
- 存量规则、操作生效范围和既有能力组合是否与变更一致：通过/不通过/不适用
- 问题与修订：...

## 6. 语言与一致性审查
- 标题、术语和结构是否符合用户指定样式；无指定样式时是否采用中性标题：通过/不通过
- 是否使用明确的主语、对象、条件和结果，未以空泛评价替代规则：通过/不通过
- 共性规则与指标是否只定义一处，图文及跨端引用是否一致：通过/不通过
- 历史数据是否标明来源、时间和适用性：通过/不通过
- 问题与修订：...
```

问题驱动的审查优先于打分。没有发现问题时再核对关键的失败情形；仍无问题可以明确给出结论，不为评分或条数制造缺口。只读审查不受下面的评分和继续修订要求驱动。

### 步骤 9：评分（内部使用）

评分只用于完整生成或评审精简稿的内部辅助检查，不用于只读审查或局部修订，不默认写进最终 PRD。不适用的维度不计分，按适用项总分归一化；评分不能覆盖关键缺口，也不代表已完成真实的产品验收。

| 维度 | 分值 |
|---|---:|
| 背景与目标 | 10 |
| 用户与场景 | 10 |
| 范围控制 | 15 |
| 功能完整性 | 20 |
| 交互完整性 | 15 |
| 状态与异常 | 15 |
| 数据与指标 | 10 |
| 验收可执行性 | 5 |

低于 85 分继续修订。出现以下任一情况直接判定未完成：

1. 核心流程未闭合。
2. 未明确本期范围。
3. 存在可能发生的失败情形，却未定义处理与恢复。
4. 指标没有口径却写成目标承诺。
5. 擅自修改已确认的业务规则。
6. 外部接口章节替研发定义了协议。
7. 无法形成可测试的验收标准。
8. 用户已有成稿时，未对齐成稿的结构和语言。
9. 未经业务确认就自行豁免既有下游处理（如自动应答、分配、提醒、统计考核），或把其他项目的豁免策略当成本项目的既定规则。

异步通知的频控需分别检查业务身份、具体动作、各自或合计上限、次数窗口与重置条件。去重不得阻止失败部分的恢复；结果未知时先核查，状态未确认不能继续执行。详见 [成稿审查与事件通知规则](review-and-notification-rules.md)。

## 验证步骤（未通过则任务未完成）

交付前按 [通用方法](requirement-method.md) 核对适用项。正文不批量呈现“不适用”，也不为完成清单扩展范围。静态检查、人工规则审阅、Agent 行为测试与真实产品验收分别报告。

用户成稿和异步事件需求还需完成 [专项检查](review-and-notification-rules.md#7-使用前后检查)，并按 [检查样例](review-regression-cases.md) 核对相关行为。只读审查只应用其范围内的检查项；在线变更还须完成目标核对、并发检查和保存后回读。

### 2. PRD 完整性清单

需求层：

- [ ] 问题清楚。
- [ ] 本期范围清楚。
- [ ] 存在容易误解的排除项时，非目标清楚。
- [ ] 指标处理清楚，没有乱写目标承诺。

功能层：

- [ ] 页面/位置清楚。
- [ ] 展示规则清楚。
- [ ] 默认状态清楚。
- [ ] 入口展示/隐藏条件清楚。
- [ ] 权限、弹窗、取消、处理中、成功、失败等状态清楚。
- [ ] 异常处理清楚，并说明是否继续、是否进入下游、是否生成记录、是否可重试。
- [ ] 多端差异清楚。

- [ ] 数据记录清楚。

系统层：

- [ ] 数据来源清楚。
- [ ] 外部依赖清楚。
- [ ] 产品侧数据需求清楚。
- [ ] 没有替研发定义接口协议。
- [ ] 降级和回滚清楚。

验收层：

- [ ] 验收标准能转成测试用例。
- [ ] 覆盖边界值、空值、失败、超时、权限、多端。

### 3. AB 条件检查

仅当原始材料或用户要求本 PRD 包含 AB 时检查：

- [ ] 明确实验目标。
- [ ] 明确实验组和对照组。
- [ ] 明确分流单位和实验桶稳定性。
- [ ] 明确核心指标和护栏指标。
- [ ] 用户明确要求埋点时单独输出埋点章节；未要求时，链路和功能需求中不写埋点。
- [ ] 验收标准覆盖实验组可见、对照组不可见、实验桶稳定。

用户说明 AB 还没写或后续另写时，不做上述硬性检查，只在待确认或后续事项中保留。

### 4. 禁止项检查

全文检查以下问题，出现任一项必须修订：

1. 未明确跨端差异，或未界定适用范围就笼统写“同上”；已明示范围的公共规则引用可以使用。
2. 使用“优化体验”“提升效率”等无口径表述。
3. 只写主流程，没有异常和兜底。
4. 写了指标目标但没有统计口径。
5. 混淆已有能力和本期新增能力。
6. 把待确认问题写成确定规则。
7. 擅自修改用户明确要求保留的逻辑。
8. 验收标准无法转成测试用例。
9. 把代码线索写成技术方案。
10. 在评审精简稿中塞入内部评分、审查报告和长篇方法论。
11. 未取得代码访问，却把现状写成已核对的事实。

### 5. Mermaid 图验证

PRD 中包含 Mermaid 图时，必须完成渲染验证，例如使用 [mermaid-cli](https://github.com/mermaid-js/mermaid-cli)：

```bash
mmdc -i <流程图.mmd> -o <流程图.png> -b white
```

判定标准：

- 能正常渲染成图片。
- 主链路没有明显的线条交叉。
- 不同系统已用颜色或分组区分。
- 节点文字不拥挤，长文本用 `<br/>` 换行。
- 存在多条回流线、交叉线或系统边界不清时，重画后再交付。

## 常见错误与处理

| 错误现象 | 根本原因 | 处理方法 |
|---|---|---|
| 模型一上来就生成全文，内容建立在猜测上 | 跳过了就绪度问诊 | 先输出就绪度表，就阻塞项集中提问 |
| 模型连续多轮追问，迟迟不动手 | 把可假设项也当阻塞项 | 一轮最多 5 问；低影响项写默认假设，进入待确认 |
| 输出很长，但研发仍然无法评审 | 套完整方法论模板，没有贴合评审稿形态 | 切换评审精简稿模式，保留链路、规则、接口、验收 |
| 用户已有 PRD 被改写成另一种风格 | 没有学习用户成稿的语言和布局 | 先提取标题、章节、表格、链路写法，再按原风格改 |
| BRD 中的后续内容被写进本期 | 没有压力测试范围 | 先写本期范围和非目标；主动收敛的内容不回灌 |
| PRD 看起来完整，但业务逻辑不可信 | 把推断写成事实 | 关键结论标注来源，推断移入默认假设或待确认 |
| 现状描述看似权威但没有依据 | 没有代码访问却写成已核对 | 标明访问级别；L0 时现状结论全部标待确认 |
| 多端规则冲突 | 差异或公共规则的适用范围不明确 | 共性规则只定义一处，按终端说明差异与引用范围 |
| 用户既定方案被替换 | 只套通用模板，没有尊重用户成稿逻辑 | 保留用户已写的入口、操作方式、页面结构、提示口径和流程顺序；只补缺口、修冲突 |
| 只有正常路径，没有失败处理 | 没有核对实际状态与异常 | 补充本期可能发生的失败与恢复情形；无关状态不补写 |
| 异常处理散落且口径冲突 | 没有集中收口失败状态 | 用“失败情况 | 处理逻辑”表统一说明 |
| 策略失败提示暴露判断细节 | 把策略判断直接展示给用户 | 改为“按现有策略失败口径提示，具体文案以策略方确认为准” |
| 外部依赖章节只有对接人 | 没有写可验收的口径 | 补齐输入与输出、展示、历史查询、失败兜底和是否复用现有逻辑 |
| 指标不可验收 | 只有指标名称，没有口径 | 补齐统计对象、事件、时间窗、去重逻辑、分子分母、数据源 |
| 指标目标乱写 | BRD 只有估算或方向，没有完整口径 | 改为“上线后观察指标”或“待数据侧确认” |
| 查询链路说明过重 | 同时写长段落、明细表和流程图 | 改为现有链路 / 本期变更；简单链路不强制画图 |
| 可变状态标签缺少刷新规则 | 只写展示条件，没有说明状态变化后的处理 | 补充查询时机、重新查询时机、是否实时刷新、失败兜底 |
| 产品替研发定义接口字段 | 把 PRD 当技术方案 | 改为“数据需求 / 业务含义 / 用途 / 异常处理要求” |
| 代码线索喧宾夺主 | 把检索结果写成正文主体 | 正文只保留产品边界结论，路径放末章代码线索 |
| AB 被机械强塞或机械删除 | 没有判断用户意图 | 按完整生成、后续另写、移出本期三种情况处理 |
