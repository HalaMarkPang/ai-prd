# 通用需求分析与表达方法

本文件适用于跨业务 PRD 的生成、修订、审查与样本学习。它定义分析方法，不规定业务参数、技术方案或统一的正文目录。用户当前授权、已确认规则和指定模板优先；仅学习或审查时，不进入正文生成和写入。

## 1. 与执行流程的关系

以下六个分析阶段嵌入 [PRD 生成规则](prd-generation.md) 的既有步骤，不增加第二套流程或额外产物。阶段开始前先完成 [就绪度问诊](intake.md)。完整生成保留既有内部产物；局部修订仅分析受影响部分，只读审查不重新论证全部既定需求。

| 分析阶段 | 对应执行步骤 | 应形成的判断 |
|---|---|---|
| 问题与目标 | 步骤 2—3：材料与评估 | 问题证据、原因确定程度、建设目标及方案必要性 |
| 变更基线 | 步骤 4—5：事实与按需查证 | 现有能力、本期变更、保持不变、非目标和实施前提 |
| 业务模型 | 步骤 6：需求建模 | 角色、对象、数据范围、操作和状态之间的关系 |
| 规则定义 | 步骤 6—7：建模与正文 | 条件、处理、结果和后续状态；按需补充时效与异常 |
| 数据、交互与依赖 | 步骤 5—7：查证、建模与正文 | 口径、可见行为和责任分工一致，未经确认的实现不固化 |
| 验证与交付 | 步骤 8—9及验证步骤 | 规则可检验、来源可追溯、未决项及本轮完成范围明确 |

阶段之间允许返回修订。初始评估不是不可变结论；后续查证推翻关键前提时，重新评估，说明受影响范围，不继续依照失效假设生成。

完整评估结论与完整正文定论，须在本轮指定材料完成通读后给出；方法见 [§3](#3-材料通读与样本使用)。

## 2. 问题澄清与需求评估

建立“现状事实 → 问题证据 → 原因判断 → 建设目标 → 方案选择”的关系。用户反馈提供体验问题证据，技术成因通过定向查证确定；竞品能力作为方案参考，必要性由本期问题和约束判断。

### 2.1 陈述分层

材料与对话中的表述先按下列类型区分，再进入评估或建模。类型混写时不得一并当作已确认事实。

| 类型 | 含义 | 处理 |
|---|---|---|
| 可验证事实 | 有来源、可核对的现状或数据 | 标注来源；关键项可附证据可信度 |
| 对事实的解释 | 由事实推出的原因或机制判断 | 标明推理链；证据不足时列为假设 |
| 价值判断 | 优先级、体验偏好或应然主张 | 不单独构成建设依据，须对照问题与约束 |
| 本期目标 | 期望达成的可观察结果 | 与事实、约束对照后写入建设目标 |

### 2.2 问题澄清

目标含糊、关键词所指不明、关键前提未证实，或表面问题与真实诉求可能不一致，且该未知可能改变建设与否、范围或方案选择时，先澄清再建模或编写正文。不影响上述判断的缺项，列明假设后继续。

**与就绪度问诊的分工**：任务开场按 [就绪度问诊](intake.md) 集中一轮（至多 5 个问题）盘点阻塞项。进入需求评估后，对仍会影响建设结论的关键未知，按本节一次只问一个问题；不为凑数量追加问卷。两阶段不得互相顶替。

可与用户交互时：

1. 每次只提出一个问题，且该问题可能改变建设与否、范围或方案选择。
2. 提问前用一句话说明上一条信息更新了哪项判断。
3. 优先核对含糊术语、默认前提、证据来源、相反解释，以及结论成立与不成立的影响。
4. 信息足以支撑评估时停止提问，不为满足提问数量而追加问题，不一次性列出问卷式清单。
5. 澄清结束后整理初始表述、真正待解决的问题、已确认事实、未验证假设、最可能改变结论的变量，以及可继续执行的具体问题；用户确认后给出评估结论。

无法与用户交互时（如 CI、批处理或其他无人值守运行），不中止任务：将关键澄清问题按影响排序记入评估，写明采用的假设及其对结论的影响，并在 PRD 待确认章节中列明责任和确认条件。

**澄清问题与待确认事项用途不同**：澄清问题在交付前逐一处理；待确认章节记录交付时仍未决的事项。不以待确认清单替代本应完成的澄清。

权限、资格、不可逆动作或高影响结果的关键未知，须先核实或集中确认，不以假设代替。

### 2.3 评估结构

新建需求评估真实性、必要性、替代方案和范围。评估须区分：

| 项目 | 内容 |
|---|---|
| 不可绕开的基本事实 | 已确认且本期无法回避的约束与现状 |
| 未验证假设 | 习惯性接受、材料默认成立、但尚未证实的前提 |
| 建设目标 | 与问题证据对应的可观察结果 |
| 资源与约束 | 排期、依赖、存量行为、跨团队条件等现实限制 |

评估时不以行业惯例或既有方案表述为前提，从基本事实、目标与约束重新核对建设是否成立。指出仅修补表面现象的部分；必要时给出由基本事实重新推导的路径及其成立前提。

存在两个及以上可行方向时，在给出结论前完成对峙论证：

1. 准确、完整地重述真正需要做出的选择。
2. 各方分别写明最强理由、适用条件、最大收益、最大风险，以及最难回答的反对意见。
3. 归纳共同认可的事实、真正分歧、分歧背后的假设，以及最可能改变结论的变量。
4. 仍缺一项关键信息时，可交互则只询问该问题，不可交互则按 2.2 记录假设；信息足够后给出明确结论。

结论采用建议建设、调整范围、采用替代方案或建议暂缓，并说明依据、适用条件、主要风险与未知限制。后续证据改变前提时更新评估；局部修订仅核对变更影响；只读审查围绕指定范围反馈。

不能因暂缺证据就断言不存在需求，也不能为推进生成而补造事实。

## 3. 材料通读与样本使用

### 3.1 通读完成条件

完整评估结论与完整正文定论，须在本轮指定的有效材料（BRD、成稿、说明、必要附件）完成范围内通读后给出。不得以上下文篇幅、开头内容或导航摘要为由提前结束阅读。

| 要求 | 说明 |
|---|---|
| 覆盖记录 | 记录已读范围；有意跳过项（模板占位、删除线、明确范围外、无法读取）须写明理由 |
| 中途材料 | 章节导航、材料包摘要、分段摘录仅用于定位原文，不得替代通读结论 |
| 部分读取 | 仅完成部分范围时，只给出限定于已读部分的阶段判断，并说明未读部分对评估、建模与正文的影响；不得表述为完整结论 |
| 来源锚点 | 影响结论的关键事实与规则保留可回查位置（文档、章节或标题、必要段落）；审查时按锚点回原文核对 |

长文档按章节或自然分段依次读取并更新覆盖记录；全部指定范围处理完毕前，不得表述为“分析已完成”。局部修订与只读审查仅须通读本轮授权及相关联动部分。

### 3.2 材料处理步骤

1. 读取相关正文、表格、批注、图片和必要附件，记录来源、版本、确认状态、读取缺口与覆盖记录。读取方法见 [材料来源](doc-sources.md)。
2. 当前有效内容、历史删改、候选方案、模板占位及多人协作内容分别标识。删除线不恢复为当前规则；问句、占位示例和空章节不视为已经完成的设计。
3. 来源冲突按用户当前说明和明确确认记录核对；仍有歧义时列明具体分歧及影响，不凭排版、篇幅或出现顺序自行定案。
4. 样本学习提取可迁移的结构、规则表达及判断方法，具体业务参数保持项目归属；审查学习可采用反向拆解：先概括其解决的问题，再分析服务对象、结构选择、质量差距与可迁移规律。
5. 文档所有者、协作作者和模板来源分别依据可确认信息说明；不作超出证据的归因。
6. 原型与示意图仅支撑明确可见的布局、标注与操作；文字定义业务条件、处理与结果。超出图像证据的行为、手势与状态进入待确认。用户明确要求可点击 HTML 原型作为验证附件时，该产物独立于 PRD 正文，不改变默认正文结构，也不替代规则定义。细则见 [截图与原型](doc-sources.md#3-截图与原型)。
7. 抽象项须满足：跨场景成立、能够指导判断、适用条件明确、不代替业务或研发决策。一次出现的做法只作为候选，不宣称已验证为通用方法。
8. 技能只保存通用规则和合成检查情形，不携带原项目文档标识、人员、业务数据、固定次数、时限、文案或技术路径。

## 4. 变更基线

| 类型 | 核对内容 |
|---|---|
| 现有能力 | 当前实现、适用条件及复用依据 |
| 本期变更 | 新增、调整或取消的行为，以及对应问题 |
| 保持不变 | 易被连带理解为变更、实际继续沿用的规则 |
| 非目标（范围排除） | 已明确排除的对象、终端、功能和后续事项 |
| 实施前提 | 尚待具备的能力、配置或跨团队条件及影响 |

“非目标”与“范围排除”同义，正文采用用户模板用词即可。

涉及配置或默认规则调整时，再检查新增对象初始化、存量迁移、人工配置保留、继承关系与冲突处理。未涉及存量时不另设迁移章节；已明确不迁移时不擅自增加数据变更。

### 4.1 本期变更的组合场景

知识材料未命中或未配置时，仍按实际变更核对下列关系。只展开本期存在且会影响结果的组合。

| 变更特征 | 重点核对 |
|---|---|
| 新入口或新动作 | 角色权限、数据范围、动作生效对象、入口之间的共用规则 |
| 新状态或条件 | 进入退出条件、规则优先级、终态、历史状态下的操作 |
| 自动或异步执行 | 资格时效、业务身份、重复触发、未知结果、部分成功及恢复 |
| 存量规则调整 | 新增对象、历史对象、人工配置、继承、迁移和回滚边界 |
| 新内容进入既有链路 | 查询、引用、导出、通知、统计、历史记录和跨端兼容 |
| 外部能力复用 | 提供方与消费方、失败传播、数据时效、运行前提及责任边界 |
| AI/Agent 动作 | 可见输入、工具参数来源、执行资格、结果核实、人工确认及失败恢复 |

## 5. 业务模型与规则定义

### 5.1 模型关系

分别识别角色、业务对象、工作上下文、数据范围、允许操作和对象状态。权限判断不能只按角色数量决定：单角色也可能存在不同数据范围或操作限制。

- **操作权限**：主体可以执行什么操作，无权限时如何表现。
- **数据范围**：主体可以查看、选择、修改哪些对象；不同操作的范围可能不同。
- **工作上下文**：当前处于哪个组织、区域、项目、工作区或聚合视图。
- **生效对象**：某次动作实际改变哪个实体或集合，不因聚合展示而默认扩大。

只展开实际存在且影响结果的组合，不机械穷举全部维度。

### 5.2 规则单元

每条关键规则以“适用对象与条件 → 触发 → 校验与处理 → 结果与反馈 → 后续状态”为分析单元。字段是检查维度，不要求正文逐条套相同长句。

| 适用条件 | 应检查的问题 |
|---|---|
| 多条件或多规则同时命中 | 条件是否互斥、可叠加；优先级与冲突结果是否明确 |
| 对象有状态变化 | 状态如何进入、退出或终止；旧状态下的操作是否仍有效 |
| 操作影响多个对象或多次编辑 | 当前对象或集合、本次或历史内容、暂存或生效；撤销、取消、重置的恢复基准 |
| 新能力与既有功能组合 | 既有操作、查询、历史记录和实际涉及终端/版本是否兼容 |
| 延迟、重复、并发或部分成功 | 业务身份、资格、计次、结果核实及恢复范围；按 [异步专项](review-and-notification-rules.md#4-去重重试和状态校验必须兼容) 检查 |
| 失败需要人工介入 | 保留哪些结果、用户下一步动作、处理责任及终止条件 |

没有实际场景的检查项跳过。权限、不可逆动作及高影响结果存在关键未知时，不按允许执行补全，也不以“合理假设”代替确认。

### 5.3 时间与结果语义

区分展示信息、执行资格和历史记录：

- 展示信息：明确允许的时效、获取与刷新时机，不默认全部实时。
- 执行资格：明确何时必须确认有效、谁负责确认，以及无法确认时如何处理。
- 历史记录：明确保存当时内容还是展示最新结果；历史入口能否继续操作另行判断。

这些是产品要求，不预设轮询、订阅、缓存、锁或存储方案。已确认实现可引用其依据；一次查询不等于解决全部并发问题。

## 6. 数据、交互与依赖

### 6.1 数据口径

有数据依赖时，说明来源、业务含义、统计或关联范围、计算口径、时效与缺失处理。零值、空结果、失败、未知和无权限分别解释，不将查询失败呈现为业务零值。

展示数据无法取得时是否隐藏、提示或阻断，应由其对主流程的影响决定；执行资格无法确认时不得直接放行。数据由谁计算、由谁聚合，按已确认职责说明，不统一指定前后端实现。

### 6.2 交互表达

对有界面的需求，原型负责布局和交互位置，文字定义可执行规则。明确入口、默认状态、动作条件、操作过程、结果反馈和恢复路径。没有界面的变更不强制补页面与弹窗。

图示或截图没有明确的行为不能靠视觉推断补全。共性规则集中定义，差异按实际角色、终端或场景补充；只有适用范围和引用对象明确时，才使用“同公共规则”“沿用现有逻辑”。

### 6.3 协作责任

外部依赖应说明提供方、消费方、需要的信息或能力、业务含义、结果如何使用及确认状态。只写系统名与对接人不足以界定责任。

来源未经确认时不自定字段、协议或技术参数。业务责任与工程实现分开；不将一种查询架构、显示身份或失败策略推广至所有项目。

## 7. 内容组织与语言

1. 先确定任务模式，再选择表达规模。完整生成、评审精简稿、局部修订、只读审查不应产生相同交付物。
2. 分析内容覆盖问题目标、范围变更、方案规则、依赖约束、验证与待确认；这些不必全部成为独立章节。已有成稿或指定模板优先，没有模板时按信息关系选最简结构。
3. 单一结论用短段落，多条件映射用决策表，多角色差异用矩阵，复杂关系或时序才用图；不按每个历史案例新增专用模板。
4. 同一规则只在一处完整定义。页面、流程、数据和验收可以引用，不能形成冲突的多份定义。
5. 先结论后依据；使用明确主语、动作、对象与条件。“相关”“当前”“有效”“适当”等词需要可识别范围，不用“优化体验”“合理处理”替代验收行为。
6. 保留用户明确的术语、标题、结构与已确认规则。新稿默认使用中性标题；不因通用排版偏好重命名已有成稿。
7. 内部检查中的“不适用”不批量写入正文；在需要澄清范围排除时才说明。样本中空章节不成为新稿模板要求；未获授权不删除原稿章节。

## 8. 验证与交付

| 验证类别 | 核对内容 | 不可替代的边界 |
|---|---|---|
| 功能正确性 | 规则对应的前提、动作和可观察结果；适用的正常、边界及异常情形 | 页面存在或接口可用，不等于业务规则正确 |
| 运行质量 | 本次变更相关的性能、稳定性、安全、兼容要求 | 未确认时不补造 SLA、容量或技术参数 |
| 业务效果 | 指标口径、来源、观察窗口、基线及归因方式 | 预期收益、观察结果和因果结论分别表述 |

关键规则应能对应验收情形；可以落在原功能条目中，不要求每次新增独立验收表。未确认事项说明影响和处理责任，不以高评分抵消缺口。

灰度、回滚、迁移、实验仅在适用且属于当前交付范围时检查。交付说明实际读取、查证、修改和验证范围；静态格式检查、规则审阅、Agent 行为测试、真实产品验收分别报告，未执行的不标为通过。

合成情形见 [检查样例](review-regression-cases.md#通用方法检查样例)。
