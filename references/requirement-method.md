# 通用需求分析与表达方法

本文件适用于跨业务 PRD 的生成、修订、审查与样本学习。它定义分析方法，不规定业务参数、技术方案或统一的正文目录。用户当前授权、已确认规则和指定模板优先；仅学习或审查时，不进入正文生成和写入。

## 1. 与执行流程的关系

以下六个分析阶段嵌入 [PRD 生成规则](prd-generation.md) 的既有步骤，不增加第二套流程或额外产物。阶段开始前先完成 [就绪度问诊](intake.md)。完整生成保留既有内部产物；局部修订仅分析受影响部分，只读审查不重新论证全部既定需求。

| 分析阶段 | 对应执行步骤 | 应形成的判断 |
|---|---|---|
| 问题与目标 | 步骤 2—3：材料与评估 | 问题证据、原因确定程度、建设目标及方案必要性 |
| 变更基线 | 步骤 4—5：事实与按需查证 | 现有能力、本期变更、保持不变、非目标和实施前提 |
| 业务模型 | 步骤 6：需求建模 | 角色、对象、数据范围、操作和状态之间的关系 |
| 规则定义 | 步骤 6—7：建模与正文 | 条件、处理、结果和后续状态；按需补充时效与异常 |
| 数据、交互与依赖 | 步骤 5—7：查证、建模与正文 | 口径、可见行为和责任分工一致，未经确认的实现不固化 |
| 验证与交付 | 步骤 8—9及验证步骤 | 规则可检验、来源可追溯、未决项及本轮完成范围明确 |

阶段之间允许返回修订。初始评估不是不可变结论；后续查证推翻关键前提时，重新评估，说明受影响范围，不继续依照失效假设生成。

## 2. 材料与样本使用

1. 阅读相关正文、表格和必要图示；记录来源与版本，说明未能读取的部分，不以标题或摘要代替完整材料。
2. 区分当前有效内容、历史删改、候选方案、待确认内容与模板残留。删除线不恢复为当前规则；问句、占位示例和空章节不视为已经完成的设计。
3. 图与文冲突、不同版本冲突时，按明确的确认记录处理；没有确认依据则保留歧义，不凭排版、篇幅或出现顺序自行定案。
4. 文档所有者不等于全部内容的独立作者。学习多人协作稿时，区分可确认的个人表达、公共模板与其他协作章节，不作超出证据的归因。
5. 抽象项须满足：跨场景成立、能够指导判断、适用条件明确、不代替业务或研发决策。一次出现的做法只作为候选，不宣称已验证为通用方法。
6. 技能只保存通用规则和合成检查情形，不携带原项目文档标识、人员、业务数据、固定次数、时限、文案或技术路径。

## 3. 问题与变更基线

### 3.1 问题论证

建立“现状事实 → 问题证据 → 原因判断 → 建设目标 → 方案选择”的关系。用户反馈证明存在某种体验问题，不直接证明技术成因；竞品功能提供参考，不单独证明建设必要性。

评估已有能力、替代方案与缩减范围的可能性。结论说明依据及限制；不能因暂缺证据就断言不存在需求，也不能为推进生成而补造事实。

### 3.2 变更定义

| 类型 | 核对内容 |
|---|---|
| 现有能力 | 哪些已存在，复用依据是什么 |
| 本期变更 | 新增、修改或取消哪些行为，解决哪个问题 |
| 保持不变 | 哪些易被误认为同步变更的规则实际保持不变 |
| 非目标 | 哪些场景、对象或能力明确排除 |
| 实施前提 | 哪些外部条件尚未具备，影响什么 |

涉及配置或默认规则调整时，再检查新增对象初始化、存量迁移、人工配置保留、继承关系与冲突处理。未涉及存量时不另设迁移章节；已明确不迁移时不擅自增加数据变更。

## 4. 业务模型与规则定义

### 4.1 模型关系

分别识别角色、业务对象、工作上下文、数据范围、允许操作和对象状态。权限判断不能只按角色数量决定：单角色也可能存在不同数据范围或操作限制。

- **操作权限**：主体可以执行什么操作，无权限时如何表现。
- **数据范围**：主体可以查看、选择、修改哪些对象；不同操作的范围可能不同。
- **工作上下文**：当前处于哪个组织、区域、项目、工作区或聚合视图。
- **生效对象**：某次动作实际改变哪个实体或集合，不因聚合展示而默认扩大。

只展开实际存在且影响结果的组合，不机械穷举全部维度。

### 4.2 规则单元

每条关键规则以“适用对象与条件 → 触发 → 校验与处理 → 结果与反馈 → 后续状态”为分析单元。字段是检查维度，不要求正文逐条套相同长句。

| 适用条件 | 应检查的问题 |
|---|---|
| 多条件或多规则同时命中 | 条件是否互斥、可叠加；优先级与冲突结果是否明确 |
| 对象有状态变化 | 状态如何进入、退出或终止；旧状态下的操作是否仍有效 |
| 操作影响多个对象或多次编辑 | 当前对象或集合、本次或历史内容、暂存或生效；撤销、取消、重置的恢复基准 |
| 新能力与既有功能组合 | 既有操作、查询、历史记录和实际涉及终端/版本是否兼容 |
| 延迟、重复、并发或部分成功 | 业务身份、资格、计次、结果核实及恢复范围；按 [异步专项](review-and-notification-rules.md#4-去重重试和状态校验必须兼容) 检查 |
| 失败需要人工介入 | 保留哪些结果、用户下一步动作、处理责任及终止条件 |

没有实际场景的检查项跳过。权限、不可逆动作及高影响结果存在关键未知时，不按允许执行补全，也不以“合理假设”代替确认。

### 4.3 时间与结果语义

区分展示信息、执行资格和历史记录：

- 展示信息：明确允许的时效、获取与刷新时机，不默认全部实时。
- 执行资格：明确何时必须确认有效、谁负责确认，以及无法确认时如何处理。
- 历史记录：明确保存当时内容还是展示最新结果；历史入口能否继续操作另行判断。

这些是产品要求，不预设轮询、订阅、缓存、锁或存储方案。已确认实现可引用其依据；一次查询不等于解决全部并发问题。

## 5. 数据、交互与依赖

### 5.1 数据口径

有数据依赖时，说明来源、业务含义、统计或关联范围、计算口径、时效与缺失处理。零值、空结果、失败、未知和无权限分别解释，不将查询失败呈现为业务零值。

展示数据无法取得时是否隐藏、提示或阻断，应由其对主流程的影响决定；执行资格无法确认时不得直接放行。数据由谁计算、由谁聚合，按已确认职责说明，不统一指定前后端实现。

### 5.2 交互表达

对有界面的需求，原型负责布局和交互位置，文字定义可执行规则。明确入口、默认状态、动作条件、操作过程、结果反馈和恢复路径。没有界面的变更不强制补页面与弹窗。

图示或截图没有明确的行为不能靠视觉推断补全。共性规则集中定义，差异按实际角色、终端或场景补充；只有适用范围和引用对象明确时，才使用“同公共规则”“沿用现有逻辑”。

### 5.3 协作责任

外部依赖应说明提供方、消费方、需要的信息或能力、业务含义、结果如何使用及确认状态。只写系统名与对接人不足以界定责任。

来源未经确认时不自定字段、协议或技术参数。业务责任与工程实现分开；不将一种查询架构、显示身份或失败策略推广至所有项目。

## 6. 内容组织与语言

1. 先确定任务模式，再选择表达规模。完整生成、评审精简稿、局部修订、只读审查不应产生相同交付物。
2. 分析内容覆盖问题目标、范围变更、方案规则、依赖约束、验证与待确认；这些不必全部成为独立章节。已有成稿或指定模板优先，没有模板时按信息关系选最简结构。
3. 单一结论用短段落，多条件映射用决策表，多角色差异用矩阵，复杂关系或时序才用图；不按每个历史案例新增专用模板。
4. 同一规则只在一处完整定义。页面、流程、数据和验收可以引用，不能形成冲突的多份定义。
5. 先结论后依据；使用明确主语、动作、对象与条件。“相关”“当前”“有效”“适当”等词需要可识别范围，不用“优化体验”“合理处理”替代验收行为。
6. 保留用户明确的术语、标题、结构与已确认规则。新稿默认使用中性标题；不因通用排版偏好重命名已有成稿。
7. 内部检查中的“不适用”不批量写入正文；在需要澄清范围排除时才说明。样本中空章节不成为新稿模板要求；未获授权不删除原稿章节。

## 7. 验证与交付

| 验证类别 | 核对内容 | 不可替代的边界 |
|---|---|---|
| 功能正确性 | 规则对应的前提、动作和可观察结果；适用的正常、边界及异常情形 | 页面存在或接口可用，不等于业务规则正确 |
| 运行质量 | 本次变更相关的性能、稳定性、安全、兼容要求 | 未确认时不补造 SLA、容量或技术参数 |
| 业务效果 | 指标口径、来源、观察窗口、基线及归因方式 | 预期收益、观察结果和因果结论分别表述 |

关键规则应能对应验收情形；可以落在原功能条目中，不要求每次新增独立验收表。未确认事项说明影响和处理责任，不以高评分抵消缺口。

灰度、回滚、迁移、实验仅在适用且属于当前交付范围时检查。交付说明实际读取、查证、修改和验证范围；静态格式检查、规则审阅、Agent 行为测试、真实产品验收分别报告，未执行的不标为通过。

合成情形见 [检查样例](review-regression-cases.md#通用方法检查样例)。
