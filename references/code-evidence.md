# 代码证据

需求要在已有系统上改造，或评估依赖“某个能力是否已经存在”时，PRD 里的现状判断需要依据。依据可信，靠的不是用了什么工具，而是每条论断都能回链到核对过的 `仓库/文件:行号`。全新产品、与现状无关的概念设计不需要代码证据。

## 1. 代码访问分级

在 [就绪度问诊](intake.md#6-代码现状的问法) 中问清用户能提供哪一级访问，并在 PRD 的代码线索中注明实际采用的级别。

| 级别 | 用户情况 | 做法 | 边界 |
|---|---|---|---|
| L0 | 不提供代码 | 不检索 | 所有现状结论标为“待确认，未经代码核对” |
| L1 | 贴出代码片段、接口文档或配置 | 只基于贴出的内容判断 | 片段之外的调用方和分支不可知 |
| L2 | 仓库已在本机 | 用 Agent 自带的搜索或 `rg` 定向检索，再读源码 | 本地快照可能落后于线上分支 |
| L3 | 跨仓库、调用链复杂 | 先用代码图谱或“查找引用 / 调用层级”定位，再读源码 | 图谱只给线索 |
| L4 | 仓库在 GitHub、GitLab 等远端 | 用 `gh` 或平台的只读 API 查询 | 召回取决于平台搜索能力，通常窄于本地检索 |

- 只做读取操作，不调用任何创建、修改、删除类接口。
- token 只放在用户本机的环境变量里，使用只读权限。不要求用户把 token 粘贴进对话，也不写进 PRD 或日志。
- 未经用户同意，不把私有代码发送到第三方服务。
- 需要构建、运行测试或大范围搜索时，建议用户把仓库克隆到本地，转为 L2 或 L3。

## 2. 取证纪律

1. **定向检索。** 只围绕本需求涉及的页面、接口、状态、权限、配置和消息链路检索，不做全仓摘要。
2. **线索不是结论。** 关键词命中、图谱查询、远端路径匹配都只说明“相关”。写进 PRD 的论断，必须读到具体代码行并确认语义后才成立。
3. **闭不了环的进待确认。** 只定位到相关符号、没能沿目标链路读通的，在 PRD 中列为待确认，注明“仅线索定位，链路未闭合”，不写成根因。
4. **跨端两头都要闭环。** 涉及前后端的结论，两端分别读通后才能合并。
5. **如实标注。** 写清覆盖了哪些仓库和链路、哪些没有覆盖。远端只读不能写成已克隆或已测试，本地检索不能写成已做全量审计。

反面教训：曾有一次直接采信图谱按关键词召回的符号，把一个与目标链路无关的解析函数当成根因。回读源码后才发现，表层原因在前端过滤，根本原因在后端的主键构造。只信线索、不读源码，会同时错判根因和改造范围。

## 3. 证据怎样进入 PRD

1. 正文只保留与产品边界相关的现状结论，写在背景与目标、现有链路或规则说明中。
2. 详细路径放在末章“代码线索”表，字段为“线索 | 文件”。
3. 需要行级证据时，按 [证据档模板](../templates/evidence-template.md) 单独产出证据档，PRD 引用其中的 `文件:行号`。
4. 代码证据只支撑产品判断，不替代产品规则，也不写成技术方案。
5. 本次没有代码访问时，代码线索章节写明“本次未核对代码，现状相关结论均待确认”。
