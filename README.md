# AI-PRD

[English](README.en.md) | 中文

AI-PRD 是一套用于生成、修订和审查产品需求文档（PRD）的 Agent Skill。它规定 Agent 从需求材料到研发评审稿的工作流程、判断规则和验证标准，适用于 Claude Code、Codex、Cursor 等支持 Skill 或规则文件的 Agent 客户端。

## 解决的问题

由 AI 直接生成的 PRD，常见缺陷集中在以下五类：

1. 信息不足时仍生成全文，关键结论建立在推测之上。
2. 未判断需求是否成立，即进入方案设计。
3. 对现有系统的描述缺乏依据，与实际实现不符。
4. 套用固定模板，与团队既有格式和评审要求不一致。
5. 用户仅要求审查或局部修改，Agent 仍改写全文或修改在线文档。

## 对应机制

| 问题 | 机制 | 规则文件 |
|---|---|---|
| 信息不足仍生成全文 | 就绪度问诊：盘点材料，将八项检查标注为“已具备 / 可假设 / 阻塞”，就阻塞项集中提问一轮，每个问题附默认处理 | [intake.md](references/intake.md) |
| 未判断需求是否成立 | 需求评估前置：从真实性、必要性、替代方案、范围边界四方面给出结论；结论不成立时，先与用户对齐 | [prd-generation.md](references/prd-generation.md) |
| 现状描述缺乏依据 | 代码访问分级（L0–L4）与取证纪律：写入 PRD 的现状结论须核对至 `文件:行号`，无法核对的列为待确认 | [code-evidence.md](references/code-evidence.md) |
| 格式与团队要求不符 | 格式优先级：用户提供的模板或样稿优先；未提供时使用本技能的 PRD 模板，并按需求复杂度裁剪 | [prd-template.md](templates/prd-template.md) |
| 越权修改 | 任务模式与读写授权：区分完整生成、评审精简稿、局部修订、只读审查；未经用户明确要求，只读任务不转为写入 | [prd-generation.md](references/prd-generation.md#执行模式)、[review-and-notification-rules.md](references/review-and-notification-rules.md) |

## 工作流程

```text
确定任务模式与读写授权
→ 就绪度问诊
→ 需求评估（新建需求）/ 变更影响核对（局部修订）
→ 按需查证现状
→ 建立变更基线与业务模型
→ 定义规则、数据、交互与依赖
→ 按用户格式生成正文或修订片段
→ 审查与验证，在授权范围内交付
```

## 流程约束

1. **问诊**：问题集中于一轮提出，至多 5 个，每个问题注明提问原因与默认处理。材料齐全时不提问。
2. **只读审查**：反馈结论后结束，不生成文件，不写入任何文档。用户随后明确要求修改时，转为局部修订，并在写入前确认写入目标。
3. **修订上限**：内部审查评分低于 85 分时，至多修订两轮。仍未达标时，Agent 停止自行修订，列出未达标的维度与缺口，由用户决定补充材料、接受当前版本或转由人工处理。
4. **非交互运行**：在 CI 等无人值守环境中运行时，Agent 不提问；阻塞项与默认假设写入 PRD 开头的“生成说明”和“待确认问题”，并注明未经用户确认。

## 安装

AI-PRD 以 `SKILL.md` 为入口，并引用 `references/` 与 `templates/` 下的规则文件，安装时须保留完整目录。

| 客户端 | 安装方式 |
|---|---|
| Claude Code | `git clone https://github.com/HalaMarkPang/ai-prd ~/.claude/skills/ai-prd` |
| Cursor | 克隆至 `~/.cursor/skills/ai-prd`，或项目内的 `.cursor/skills/ai-prd` |
| Codex | 克隆至 `~/.codex/skills/ai-prd`，或在 `AGENTS.md` 中引用 `SKILL.md`，并确保整个目录可读取 |
| 其他 Agent | 指示 Agent 读取 `SKILL.md` 及其引用的全部文件；仅提供 `SKILL.md` 无法加载完整规则 |

## 使用

在对话中说明任务目标并提供相关材料。以下示例分别对应四种任务模式：

| 任务模式 | 示例 |
|---|---|
| 完整生成 | 用 AI-PRD 为“任务逾期提醒”写一份 PRD，代码在 `~/code/my-product`。 |
| 评审精简稿 | 基于这份 BRD 生成研发评审稿，按附件中的团队模板组织。 |
| 局部修订 | 只修改这份 PRD 的“异常与失败处理”一节，其他内容保持不变。 |
| 只读审查 | 审查这份 PRD，只在对话中反馈问题，不修改文档。 |

Agent 的首次回复包含需求理解、就绪度表和待确认问题。用户可逐项回答，也可回复“按默认继续”。选择后者时，Agent 将采用的默认假设写入 PRD 开头的“生成说明”和“待确认问题”。

完整过程见示例 [任务逾期提醒](examples/overdue-task-reminder/README.md)。示例中的产品、数据与代码均为虚构。

## 代码访问

涉及已有系统改造时，Agent 在问诊中确认代码访问方式，并在 PRD 中注明实际采用的级别：

| 级别 | 条件 | 现状结论的依据 |
|---|---|---|
| L0 | 不提供代码 | 无；相关结论全部标为待确认 |
| L1 | 提供代码片段或接口文档 | 仅限所提供的内容 |
| L2 | 仓库位于本机 | 本地只读检索，核对至 `文件:行号` |
| L3 | 跨仓库，调用链复杂 | 代码图谱定位后回读源码 |
| L4 | 仓库位于 GitHub、GitLab 等远端 | 平台只读接口；召回范围通常小于本地检索 |

公开仓库无需凭证。私有仓库的访问凭证仅保存在用户本机的环境变量中，Agent 不在对话、PRD 或日志中记录凭证。

## 输出约定

- PRD 正文面向研发评审。就绪度问诊结论、需求评估、输入事实与约束、需求模型、审查报告和评分属于内部过程产物，默认不写入正文。
- 关键结论标注来源：用户明确说明、原始材料、已有 PRD、代码/系统现状、合理推断或待确认。
- PRD 只描述产品侧的数据需求、业务含义和异常处理要求，不定义接口字段、错误码、超时、缓存等技术参数。
- 指标的口径、数据源、时间窗或归因方式不完整时，仅作为上线后的观察指标，不写为目标承诺。
- 功能正确性、运行质量和业务效果分别验证；未执行的测试不标记为通过。
