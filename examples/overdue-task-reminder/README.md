# 示例：任务逾期提醒

> 本示例的产品、公司、仓库、代码和数据均为虚构，只用于演示 AI-PRD 的工作方式。示例中的阈值、次数和文案不是通用默认值。

## 场景

「协作看板」是一款虚构的团队任务管理产品，有 Web 端和 iOS/Android App。任务可以设置截止时间，逾期任务在列表中显示为红色，但不会提醒任何人。

## 1. 用户输入

> 任务过了截止时间没人管，帮我出个 PRD，加个逾期提醒。代码在本地 ~/code/board 下面。

## 2. 首次响应：就绪度问诊

模型先读取本地代码目录（用户已给出路径），做了一次定向检索，然后回复：

---

**我对这个需求的理解**：为逾期任务增加主动提醒，让相关人及时处理。本次按“评审精简稿”生成新 PRD。

**就绪度**

| 项 | 状态 | 说明 |
|---|---|---|
| 任务与交付 | 可假设 | 默认输出 Markdown 到 `./overdue-reminder-prd-work/PRD.md` |
| 需求材料 | 已具备 | 一句话需求，无 BRD |
| 问题与目标 | 可假设 | 缺少问题证据；默认把“逾期后有人跟进”作为目标，效果只作观察指标 |
| 用户与场景 | 阻塞 | 提醒谁会改变功能规则和权限判断 |
| 范围 | 阻塞 | 提醒渠道和次数决定研发范围与打扰程度 |
| 现状与代码 | 已具备 | 已在 `~/code/board` 找到 `board-server`、`board-web`，可本地检索（L2） |
| 格式 | 可假设 | 未提供模板，使用本技能 PRD 模板的精简版 |
| 约束与依赖 | 可假设 | App 推送依赖现有推送通道；免打扰时段暂按“不处理”列入待确认 |

**需要你确认的问题**（不回答的按默认处理）

1. 提醒谁？
   - 为什么问：决定接收人规则，以及负责人为空时怎么处理。
   - 选项：A. 仅负责人　B. 负责人 + 创建人　C. 再加项目管理员
   - 默认：A
2. 通过什么渠道提醒？
   - 为什么问：每多一个渠道，就多一个外部依赖和失败处理。
   - 选项：A. 仅站内通知　B. 站内通知 + App 推送　C. 再加邮件
   - 默认：B
3. 提醒几次？
   - 为什么问：决定频控规则和打扰程度。
   - 选项：A. 逾期时一次　B. 逾期时一次，持续逾期 24 小时再一次　C. 每天一次直到完成
   - 默认：A
4. 有没有能说明问题的证据，比如用户反馈或数据？
   - 为什么问：用于需求评估。没有的话，效果只能作为上线后的观察指标。
   - 默认：无，按观察指标处理。

你也可以直接回复“按默认继续”。

---

## 3. 用户回答

> 1 选 B，但第一次只提醒负责人，24 小时那次再加上创建人。2 选 B，邮件下期再说。3 选 B。最近一个月客服收到 12 条“逾期任务没人跟进”的反馈。

## 4. 需求评估结论（内部产物摘要）

- 结论：**建议做，并调整范围**。
- 真伪：有 12 条用户反馈作为问题证据。现状是逾期只做视觉标记，没有任何触达，问题成立。
- 必要性：逾期任务无人跟进会直接影响团队协作，属于核心场景。
- 替代方案：仅依赖列表的红色标记已经证明不够；每日摘要邮件的打扰更低，但用户已明确邮件放到下期。
- 范围调整：免打扰时段、批量逾期合并提醒影响体验，但不阻塞主流程，列为待确认，不在本期默认实现。

## 5. 产物

| 文件 | 内容 |
|---|---|
| [PRD.md](PRD.md) | 评审精简稿 |
| [code-evidence.md](code-evidence.md) | 代码证据档（L2，本地检索 + 源码回读） |

值得注意的几处：

- 代码检索发现，前端判断逾期时没有排除“已归档”状态，与后端口径不一致。PRD 没有自行定案，而是列入待确认。
- 频控按“同一任务、同一截止时间、每类提醒最多一次”写清业务身份；修改截止时间后重新计次。
- 推送失败不影响站内通知。推送的重试沿用现有推送通道，PRD 不定义技术参数。
